# REST API: справочник эндпоинтов

> Базовый адрес локально: `http://localhost:<NGINX_PORT>/api` (порт задан в `docker/.env`).
> Все запросы и ответы в JSON. Нужно слать заголовок `Accept: application/json`.
> Авторизация: `Authorization: Bearer <token>` или cookie-сессия Sanctum.

## Формат ответов

После рефакторинга все ответы (кроме auth и списков с пагинацией) обёрнуты одинаково:

| Действие | Код | Тело |
|---|---|---|
| Чтение одной записи или списка без пагинации | 200 | `{"data": ...}` |
| Список с пагинацией (`/events`, `/orders`, `/admin/users`) | 200 | стандартный пагинатор Laravel: `{"data": [...], "current_page", "last_page", "per_page", "total", "links", ...}` |
| Создание | 201 | `{"success": true, "data": {...}}` |
| Изменение, publish, cancel | 200 | `{"success": true, "data": {...}}` |
| Удаление | 200 | `{"success": true}` (не 204) |

## Коды ошибок

| Код | Когда |
|---|---|
| 401 | не авторизован (нет или неверный токен) |
| 403 | нет прав: middleware `can:` (Policy вернула `false`) |
| 404 | не найдено (Route Model Binding) **или** запись скрыта от пользователя (чужой черновик) |
| 422 | ошибка валидации или бизнес-правила: `{"message": "...", "errors": {"поле": ["..."]}}` |
| 429 | слишком много попыток (rate limit на регистрацию или логин) |
| 502 | платёжная система недоступна или ответила ошибкой (`POST /orders/{order}/pay`) |

> **Порядок проверок:** `auth:sanctum` (401) → поиск модели (404) → `can:` / Policy (403) → FormRequest (422) → сервис (422 бизнес-правила).
> Права проверяются **до** валидации: участник, приславший кривые данные на `POST /events`, получит 403, а не 422.

## PUT или PATCH

- **`PUT`** — полная замена записи, **все обязательные поля нужно прислать заново**: категории, места, мероприятия, типы билетов. Необязательное поле (`description`), которое не прислали, станет `null`.
- **`PATCH`** — изменение одного свойства: `/me/name`, `/me/password`, `/admin/users/{user}/role`, `/admin/users/{user}/block`.

**Тело POST/PUT `/events`:** `title`, `description?`, `starts_at` (в будущем), `ends_at` (позже `starts_at`), `category_id` (существует), `venue_id` (существует).

**Параметры `GET /events`:**

| Параметр | Пример | Описание |
|---|---|---|
| `search` | `PHP` | поиск по названию (LIKE) |
| `category_id` | `2` | фильтр по категории |
| `venue_id` | `1` | фильтр по месту |
| `date_from`, `date_to` | `2026-09-01` | диапазон даты начала (`date_to ≥ date_from`) |

| `per_page` | `20` | 1–100, по умолчанию 15 |

У каждого мероприятия в списке есть поле `min_price`.

> В ТЗ пример `?category=conference` (по slug). У нас фильтр по `category_id`. ТЗ разрешает структуру на наш выбор (§19).

## Типы билетов (ТЗ §7)

> В ТЗ путь `/events/{event}/tickets`. У нас `/ticket-types`, потому что
> «tickets» в ТЗ §11 — это купленные билеты. Так не путаются две разные сущности.

| | Метод | URL | Доступ | Тело |
|---|---|---|---|---|
| ✅ | GET | `/events/{event}/ticket-types` | все (⚠️ включая типы черновика, недочёт №6) | — |
| ✅ | POST | `/events/{event}/ticket-types` | организатор этого мероприятия | `name`, `description?`, `price` (≥ 0), `quantity` (≥ 1) |
| ✅ | PUT | `/events/{event}/ticket-types/{ticketType}` | его организатор или админ | все поля, как при создании |

## Заказы (ТЗ §8, §9)

| | Метод | URL | Доступ | Описание |
|---|---|---|---|---|
| ✅ | POST | `/events/{event}/orders` | участник | создаёт заказ `pending` и резервирует билеты |
| ✅ | GET | `/orders` | авторизован | участник видит свои, организатор — заказы своих мероприятий, админ — все. Пагинация по 15 |
| ✅ | GET | `/orders/{order}` | владелец, организатор мероприятия или админ | `{"data": заказ с items}` |

**Тело `POST /events/{event}/orders`:**

```json
{
  "items": [
    { "ticket_type_id": 1, "quantity": 2 },
    { "ticket_type_id": 3, "quantity": 1 }
  ]
}
```

Правила: `items` содержит минимум 1 позицию, `ticket_type_id` не повторяются и существуют, `quantity` от 1 до 10.
Ошибки 422: мероприятие не опубликовано (`errors.event`); тип билета от другого мероприятия или билетов не хватает (`errors.items`).

**Ответ 201:**

```json
{
  "success": true,
  "data": {
    "id": 123, "user_id": 7, "event_id": 5, "total_amount": "450000.00", "status": "pending",
    "items": [ { "ticket_type_id": 1, "quantity": 2, "price": "100000.00" }, ... ]
  }
}
```

У заказа также есть поля `payment_reference` и `payment_url`. Они заполняются после `POST /orders/{order}/pay`.

## Оплата (ТЗ §8, §10)

Покупка идёт в **два запроса**: сначала создаётся заказ, потом по нему запрашивается ссылка на оплату. Почему так — в `04-PAYMENT.md` §5.

| | Метод | URL | Доступ | Описание |
|---|---|---|---|---|
| ✅ | POST | `/orders/{order}/pay` | только владелец заказа (`can:pay,order`) | создаёт платёж в платёжной системе и возвращает ссылку на оплату |
| ✅ | POST | `/payments/webhook` | **без auth**, проверка подписи `X-Signature` | результат оплаты от платёжной системы. Единственный источник истины об оплате |

**`POST /orders/{order}/pay`**, тело пустое.

| Код | Тело | Когда |
|---|---|---|
| 200 | `{"success": true, "data": {"payment_url": "http://<платёжка>/process-payment/15"}}` | ссылка создана. Повторный вызов отдаёт ту же ссылку, новый платёж не создаётся |
| 403 | — | чужой заказ |
| 422 | `errors.order`: «Оплатить можно только заказ, ожидающий оплаты.» | заказ уже не `pending` |
| 502 | `{"success": false, "message": "Платёжная система недоступна, попробуйте позже."}` | платёжка не ответила или вернула ошибку. Заказ и резерв остаются, можно повторить |

**`POST /payments/webhook`** (вызывает платёжная система, не фронт):

```
X-Signature: hmac_sha256("amount|45000000|order_id|<uuid>|status|1", PAYMENT_SECRET)

{ "order_id": "<uuid из payment_reference>", "amount": 45000000, "status": 1 }
```

| Код | Когда |
|---|---|
| 200 `{"success": true}` | обработан: `status=1` → заказ `paid`; `status=2` → заказ `cancelled` и резерв снят. Повторный вебхук по уже обработанному заказу ничего не меняет |
| 403 `Invalid signature` | подпись не совпала |
| 404 | заказа с таким `payment_reference` нет |
| 422 | невалидное тело (`status` не 1 и не 2 и т. п.) |
