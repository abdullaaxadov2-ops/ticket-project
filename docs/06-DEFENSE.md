## 1. План выступления (7–10 минут)

1. **Задача (30 сек).** Backend платформы продажи билетов. Три роли, REST API, оплата через учебную платёжную систему курса.
2. **Стек и окружение (1 мин).** Laravel 13, PHP 8.5, PostgreSQL, Redis, Docker Compose, Sanctum. Почему так — `02-ARCHITECTURE.md` §2.
3. **Архитектура (2 мин).** Слои: маршрут → FormRequest → Policy → Service → Model. Показать один запрос целиком, например покупку билетов.
4. **Модель данных (1 мин).** ER-диаграмма: мероприятие → типы билетов → заказ → позиции → (билеты). Почему `sold_count` и почему `decimal`.
5. **Самое интересное (2–3 мин).**
   - резервирование без перепродажи: транзакция и `lockForUpdate`;
   - оплата: подпись HMAC, вебхук как источник истины, идемпотентность;
   - события и очереди: `OrderPaid` → билеты и письмо.
6. **Права доступа (1 мин).** Таблица ролей, Policies, примеры 403.
7. **Тесты (1 мин).** Запуск `php artisan test`, что покрыто.
8. **Демо (2 мин).** Сценарий ниже.
9. **Что бы улучшил (30 сек).** Честно: возвраты через платёжку, кэш списков, OpenAPI-документация.

## 2. Сценарий демо (Postman или curl)

```
1. POST /api/auth/login (admin)       → токен админа
2. POST /api/categories, /api/venues  → создать категорию и место
3. PATCH /api/admin/users/{id}/role   → сделать пользователя организатором
4. POST /api/auth/login (organiser)   → POST /api/events → POST /events/{id}/ticket-types (Standard, VIP)
5. POST /api/events/{id}/publish
6. GET  /api/events?search=PHP&sort=price  (без токена: видно опубликованное)
7. POST /api/auth/login (participant) → POST /api/events/{id}/orders → POST /api/orders/{id}/pay → получить payment_url
8. Открыть payment_url → «Success» → вебхук → GET /api/orders/{id} = paid → (🛠 когда будут билеты) GET /api/tickets
8a. Показать отказ: вебхук с неверной X-Signature → 403, заказ не изменился (или прогнать PaymentTest)
9. (организатор) POST /api/events/{id}/tickets/{ticket}/check-in → второй раз 422
10. Показать отказ: участник пытается POST /api/events → 403
```

> Перед защитой: сидер с готовыми пользователями (admin, organiser, participant),
> запущены `queue:work` и `schedule:work` у нас и у платёжки, письма видны в Mailhog.

## 3. Вероятные вопросы и ответы

### Архитектура и Laravel

**Зачем сервисный слой, почему не писать всё в контроллере?**
Контроллер отвечает только за HTTP: принять запрос, вызвать сервис, вернуть ответ. Бизнес-правила (проверка наличия, резерв, транзакция) живут в `OrderCreationService`. Их можно вызвать не только из HTTP, но и из команды или Job. Их проще тестировать. Контроллер остаётся читаемым.

**Зачем Form Request?**
Этого требует ТЗ §20. Кроме того, валидация отделена от логики: до контроллера доходят только проверенные данные, а Laravel сам вернёт 422 со списком ошибок по полям.

**Policy или Gate, почему Policy?**
Gate — это отдельные проверки-замыкания. Policy — класс с правилами для одной модели (`EventPolicy::update`, `::publish`...). Правила сгруппированы по сущности, Laravel находит Policy автоматически по имени модели.

**Почему в FormRequest `authorize()` возвращает `true`?**
Права проверяются раньше, в маршруте: `->middleware('can:update,event')` вызывает `EventPolicy::update`. Все правила доступа лежат в Policies, а FormRequest занимается только валидацией. Если бы права проверялись и там, и там, правило пришлось бы поддерживать в двух местах.

**Почему права в middleware `can:`, а не `$this->authorize()` в контроллере?**
1. В `routes/api.php` одним взглядом видно и URL, и кто к нему допущен.
2. Middleware срабатывает **до** FormRequest. Человек без прав получает 403 и даже не узнаёт правила валидации. Раньше было наоборот: сначала 422, потом 403.
3. Контроллер становится ещё тоньше. Так же сделано у преподавателя (`can:update,cashbox`).

**Зачем однометодные контроллеры (`__invoke`)?**
Один класс — одно действие (`EventPublicationController`). Имя файла говорит, что он делает. Классы маленькие, их легко читать и тестировать. В маршруте не нужно писать имя метода. Минус: файлов больше, поэтому они разложены по папкам сущностей (`Event/`, `Order/`...).

**Зачем DTO (`EventData`, `CreateOrderData`)?**
Сервис получает объект с типизированными полями, а не массив из запроса. Плюсы: опечатка в поле — сразу ошибка, IDE подсказывает поля, сервис не зависит от HTTP и его можно вызвать из команды или теста. DTO собирается в `FormRequest::toDTO()` только из `validated()`, поэтому в сервис попадают лишь проверенные поля.

**Почему `PUT` для обновления, а не `PATCH`?**
По REST `PUT` — полная замена ресурса, поэтому при `PUT /events/{id}` присылаются все поля и все проходят валидацию (например, `ends_at` после `starts_at`). Частичное обновление (`PATCH`) усложняет проверки связанных полей. `PATCH` оставили там, где меняется одно свойство: `/me/name`, `/admin/users/{user}/role`.

**Почему чужой черновик отдаёт 404, а не 403?**
403 сообщает: «такое мероприятие есть, но тебе нельзя». 404 не раскрывает даже факт существования записи. Проверка — `EventPolicy::view`, вызывается через `Gate::forUser($request->user('sanctum'))`, потому что маршрут публичный и пользователь может быть гостем.

**Что делает `scopeBindings()`?**
В `/events/{event}/ticket-types/{ticketType}` Laravel ищет тип билета **только среди типов этого мероприятия** (`$event->ticketTypes()`). Если тип от другого мероприятия, будет 404. Без этого URL `/events/1/ticket-types/99` сработал бы с чужим типом.

**Почему Enum для статусов и ролей?**
Нельзя опечататься (`'publised'`), IDE подсказывает варианты, в модели настроен каст. Валидация `Rule::enum(UserRole::class)` принимает только допустимые значения.

**Что такое Route Model Binding?**
`{event}` в маршруте Laravel сам превращает в модель `Event` по id. Если записи нет, сразу отдаётся 404.

### Данные и конкурентность

**Как вы не продадите больше билетов, чем есть?**
В `OrderCreationService` всё происходит в `DB::transaction`, типы билетов читаются через `lockForUpdate()` (`SELECT ... FOR UPDATE`). Второй покупатель ждёт, пока первый не закончит транзакцию, и увидит уже обновлённый `sold_count`. Без блокировки оба прочитали бы «остался 1 билет» и оба купили бы его (race condition).

**Почему `sold_count` увеличивается при создании заказа, а не после оплаты?**
Это резерв (ТЗ §8 п.4). Пока человек платит, билеты не может купить другой. Если оплата не прошла или время вышло, резерв снимается (`cancelled` / `expired`, `sold_count -= qty`).

**Почему `decimal`, а не `float` для денег?**
Float хранит числа приблизительно (0.1 + 0.2 = 0.30000000000000004). Для денег нужна точность, поэтому `decimal(10,2)`. Платёжке передаём целое число в тийинах.

**Зачем копировать цену в `order_items.price`?**
Цена типа билета может измениться позже. Заказ должен помнить, по какой цене купили.

### Оплата

**Почему фронтенд не может сказать «оплата прошла»?**
Запрос фронта можно подделать: любой может отправить «я оплатил». Об оплате знает только платёжная система, и она сообщает нам напрямую, сервер к серверу, вебхуком с подписью. Это требование ТЗ §10.

**Как вы проверяете, что вебхук пришёл от платёжки, а не от злоумышленника?**
Подпись HMAC-SHA256. Платёжка сортирует поля, склеивает в строку `key|value|...` и считает HMAC с секретным ключом кассы. Ключ знаем только мы и платёжка. Мы пересчитываем подпись и сравниваем через `hash_equals`. Подделать подпись без ключа невозможно.

**Почему `hash_equals`, а не `==`?**
`==` прекращает сравнение на первом несовпавшем символе, поэтому время ответа выдаёт, сколько символов угадано (timing-атака). `hash_equals` сравнивает за постоянное время.

**Что если вебхук придёт два раза?**
Платёжка повторяет отправку при ошибках, так что дубли возможны. Обработка идемпотентна: если заказ уже не `pending`, отвечаем 200 и ничего не меняем. Билеты не задвоятся.

**Что если вебхук вообще не придёт?**
Платёжка сама повторяет до 5 раз (1, 2, 4, 8 минут). Платёж висит 15 минут, потом она ставит `failed` и снова шлёт вебхук, и мы отменяем заказ и снимаем резерв. Страховка на случай, если вебхук потерялся совсем или `/pay` вообще не вызывали: команда `orders:expire` по расписанию (🛠 в планах).

**Почему ссылка на оплату — отдельный запрос `POST /orders/{order}/pay`?**
1. Создание заказа — короткая транзакция с блокировкой билетов. Запрос во внешнюю систему может идти секунды, его нельзя держать внутри транзакции.
2. Если платёжка недоступна, мы отвечаем 502, но заказ и резерв остаются. Фронт просто повторяет `/pay`, пользователю не нужно заново выбирать билеты.
3. Повторный `/pay` отдаёт ту же сохранённую ссылку, второй платёж не создаётся.
ТЗ §8 описывает шаги покупки, а §19 разрешает самим выбрать структуру API. Для фронта это два запроса подряд.

**Почему в платёжку уходит UUID, а не номер заказа?**
Платёжка требует, чтобы `order_id` был уникален в пределах кассы. После `migrate:fresh` или в тестах номера заказов снова начнутся с 1, и платёжка ответила бы «order_id уже занят». UUID уникален всегда. Он хранится в `orders.payment_reference`, по нему вебхук находит заказ. Заодно снаружи нельзя перебрать номера чужих заказов.

**Почему 502, а не 500?**
500 — «сломались мы». 502 Bad Gateway — «мы работаем, но сервис за нами не ответил». Так фронт и логи сразу видят, где проблема.

**Почему неверная подпись — 403, а неизвестный заказ — 404, а не 500?**
Платёжка повторяет вебхук только на 5xx. Запрос с неверной подписью или по несуществующему заказу от повтора не исправится, поэтому отвечаем 4xx: «запрос плохой, не повторяй».

**Почему запрос в платёжку не внутри транзакции?**
Внутри транзакции держатся блокировки строк. Если платёжка отвечает 5 секунд, все остальные покупатели этих билетов 5 секунд ждут. Поэтому сначала короткая транзакция (резерв), потом HTTP-запрос.

**Что если платёжка недоступна?**
`Http::...->throw()` бросает исключение, `PaymentCreationService` превращает его в `PaymentSystemException`, контроллер отвечает 502 «Платёжная система недоступна, попробуйте позже». Заказ остаётся `pending` с резервом, `/pay` можно повторить.

### События, очереди, Scheduler

**Зачем очереди?**
Отправка письма занимает секунды, к тому же SMTP может быть недоступен. Если делать её прямо в запросе, пользователь ждёт, а при ошибке запрос падает. В очереди задача выполняется отдельным процессом (`queue:work`) и повторяется при сбое.

**Зачем Events и Listeners?**
Это слабая связность. Код оплаты только сообщает «заказ оплачен» (`OrderPaid`), а кто на это реагирует (билеты, письмо, уведомление организатору), решают listeners. Новую реакцию можно добавить, не трогая логику оплаты.

**Как работает напоминание за 24 часа?**
Scheduler раз в час (или в минуту) запускает команду. Она находит мероприятия, которые начнутся через 24 часа, и ставит письма владельцам билетов в очередь. Чтобы письмо не ушло дважды, сохраняется отметка `reminder_sent_at`.

### Аутентификация и безопасность

**Почему не Breeze или Fortify?**
Их запрещает ТЗ: аутентификация сделана самостоятельно на Sanctum. Есть регистрация, подтверждение email кодом, логин (токен или cookie), logout с удалением токена.

**Чем отличаются режимы token и cookie?**
Для запросов с «своего» домена SPA (`SANCTUM_STATEFUL_DOMAINS`) используется сессия в cookie: токен не хранится в JS, XSS не сможет его украсть. Для остальных клиентов (Postman, мобильные) выдаётся Bearer-токен.

**Как защищён логин от перебора?**
Rate limiter: 3 неудачные попытки на email за 30 минут, регистрация не чаще 10 раз за 30 минут с одного IP. Заблокированный админом пользователь войти не может.

**Как защищены маршруты?**
Всё, кроме публичного чтения (мероприятия, категории, места, типы билетов) и вебхука, находится в группе `auth:sanctum`. Каждое действие дополнительно проверяется Policy. Вебхук без auth, но с проверкой подписи.

### Тесты

**Как тестировали?**
Feature-тесты на каждую фичу: успешный сценарий, права (401 гость, 403 чужая роль или чужая запись), валидация (422), бизнес-правила (например, нельзя купить больше остатка). База пересоздаётся на каждый тест (`RefreshDatabase`), данные берутся из фабрик. Внешнюю платёжку подменяем через `Http::fake()`, письма и очереди — через `Mail::fake()` и `Queue::fake()`.

**Что такое TDD у вас?**
Для части фич сначала писали тест (что должно происходить), потом код, пока тест не станет зелёным. Это видно в истории коммитов («политика и TDD»).

## 4. Глоссарий

| Термин | Простыми словами |
|---|---|
| REST API | адреса-«ресурсы» (`/events/5`) и HTTP-методы (GET читать, POST создать, PUT заменить целиком, PATCH изменить часть, DELETE удалить) |
| Middleware | фильтр перед контроллером (например, «пользователь авторизован?») |
| Policy | класс с правилами «кто что может делать с моделью» |
| Form Request | класс с правилами валидации входных данных |
| Транзакция | группа операций с БД: либо все применяются, либо ни одна |
| `lockForUpdate` | блокировка строки до конца транзакции, другие ждут |
| Race condition | два процесса одновременно читают и пишут одни данные, и результат ломается |
| Webhook | запрос, который внешний сервис сам отправляет нам при событии |
| HMAC | подпись сообщения секретным ключом, подтверждает автора и целостность |
| Идемпотентность | повтор одного и того же запроса не меняет результат |
| Queue / Job | фоновая задача, выполняется отдельным процессом |
| Scheduler | планировщик, запускает команды по расписанию (как cron) |
| DTO | простой объект только для переноса данных |
| Однометодный контроллер | контроллер с единственным методом `__invoke`, одно действие на класс |
| `scopeBindings` | поиск вложенной модели из URL только внутри родительской |
| Factory | генератор тестовых записей для моделей |
