## 2. Вероятные вопросы и ответы

### Архитектура и Laravel

**Зачем сервисный слой, почему не писать всё в контроллере?**
Контроллер отвечает только за HTTP: принять запрос, вызвать сервис, вернуть ответ. Бизнес-правила (проверка наличия, резерв, транзакция) живут в `OrderCreationService`. Их можно вызвать не только из HTTP, но и из команды или Job. Их проще тестировать. Контроллер остаётся читаемым.

**Зачем Form Request?**
Этого требует ТЗ §20. Кроме того, валидация отделена от логики: до контроллера доходят только проверенные данные, а Laravel сам вернёт 422 со списком ошибок по полям.

**Policy или Gate, почему Policy?**
Gate — это отдельные проверки-замыкания. Policy — класс с правилами для одной модели (`EventPolicy::update`, `::publish`...). Правила сгруппированы по сущности, Laravel находит Policy автоматически по имени модели.

**Почему в FormRequest `authorize()` возвращает `true`?**
Права проверяются раньше, в маршруте: `->middleware('can:update,event')` вызывает `EventPolicy::update`. Все правила доступа лежат в Policies, а FormRequest занимается только валидацией. Если бы права проверялись и там, и там, правило пришлось бы поддерживать в двух местах.

**Почему права в middleware `can:`, а не `$this->authorize()` в контроллере?**
1. В `routes/api.php` одним взглядом видно и URL, и кто к нему допущен.
2. Middleware срабатывает **до** FormRequest. Человек без прав получает 403 и даже не узнаёт правила валидации. Раньше было наоборот: сначала 422, потом 403.
3. Контроллер становится ещё тоньше. Так же сделано у преподавателя (`can:update,cashbox`).

**В каком порядке идут проверки?**
`auth:sanctum` (401) → поиск модели из URL (404) → `can:` и Policy (403) → Form Request (422) → бизнес-правила в сервисе (422). Пример: участник шлёт кривые данные на `POST /events` и получает 403, а не 422.

**Зачем однометодные контроллеры (`__invoke`)?**
Один класс — одно действие (`EventPublicationController`). Имя файла говорит, что он делает. Классы маленькие, их легко читать и тестировать. В маршруте не нужно писать имя метода. Минус: файлов больше, поэтому они разложены по папкам сущностей (`Event/`, `Order/`...).

**Зачем DTO (`EventData`, `CreateOrderData`)?**
Сервис получает объект с типизированными полями, а не массив из запроса. Плюсы: опечатка в поле — сразу ошибка, IDE подсказывает поля, сервис не зависит от HTTP и его можно вызвать из команды или теста. DTO собирается в `FormRequest::toDTO()` только из `validated()`, поэтому в сервис попадают лишь проверенные поля.

**Почему `PUT` для обновления, а не `PATCH`?**
По REST `PUT` — полная замена ресурса, поэтому при `PUT /events/{id}` присылаются все поля и все проходят валидацию (например, `ends_at` после `starts_at`). Частичное обновление (`PATCH`) усложняет проверки связанных полей. `PATCH` оставили там, где меняется одно свойство: `/me/name`, `/admin/users/{user}/role`.

**Почему чужой черновик отдаёт 404, а не 403?**
403 сообщает: «такое мероприятие есть, но тебе нельзя». 404 не раскрывает даже факт существования записи. Проверка — `EventPolicy::view`, вызывается через `Gate::forUser($request->user('sanctum'))`, потому что маршрут публичный и пользователь может быть гостем.

**Что делает `scopeBindings()`?**
В `/events/{event}/ticket-types/{ticketType}` Laravel ищет тип билета **только среди типов этого мероприятия** (`$event->ticketTypes()`). Если тип от другого мероприятия, будет 404. Без этого URL `/events/1/ticket-types/99` сработал бы с чужим типом.

**Почему Enum для статусов и ролей?**
Нельзя опечататься (`'publised'`), IDE подсказывает варианты, в модели настроен каст. Валидация `Rule::enum(UserRole::class)` принимает только допустимые значения.

**Что такое Route Model Binding?**
`{event}` в маршруте Laravel сам превращает в модель `Event` по id. Если записи нет, сразу отдаётся 404.

**Почему `publish`, `cancel`, `pay` — отдельные `POST`, а не `PUT` со статусом?**
Это действия с правилами, а не простая запись поля: опубликовать можно только черновик, оплатить только `pending`-заказ. Отдельный маршрут — отдельная Policy (`can:publish,event`) и понятная ошибка 422. Если бы статус менялся через `PUT`, клиент мог бы поставить любой статус в обход правил.

### Данные и конкурентность

**Как вы не продадите больше билетов, чем есть?**
В `OrderCreationService` всё происходит в `DB::transaction`, типы билетов читаются через `lockForUpdate()` (`SELECT ... FOR UPDATE`). Второй покупатель ждёт, пока первый не закончит транзакцию, и увидит уже обновлённый `sold_count`. Без блокировки оба прочитали бы «остался 1 билет» и оба купили бы его (race condition).

**Почему `sold_count` увеличивается при создании заказа, а не после оплаты?**
Это резерв (ТЗ §8 п.4). Пока человек платит, билеты не может купить другой. Если оплата не прошла, резерв снимается: вебхук со `status=2` (в том числе когда платёжка сама отменяет платёж через 15 минут) ставит заказ `cancelled` и делает `sold_count -= qty`. 🛠 Своя просрочка `expired` для заказов, по которым `/pay` не вызывали, в планах.

**Почему `decimal`, а не `float` для денег?**
Float хранит числа приблизительно (0.1 + 0.2 = 0.30000000000000004). Для денег нужна точность, поэтому `decimal(10,2)`. Платёжке передаём целое число в тийинах. Про то, что сумма заказа в PHP всё же считается во float, — в §3.

**Зачем копировать цену в `order_items.price`?**
Цена типа билета может измениться позже. Заказ должен помнить, по какой цене купили.

**Почему `lockForUpdate`, а не другой способ?**
Есть три подхода:
1. **Пессимистичная блокировка** `lockForUpdate` (у нас). Строки типов билетов заблокированы до конца транзакции, все позиции заказа проверяются разом. Просто и понятно.
2. **Атомарный UPDATE с условием**: `UPDATE ticket_types SET sold_count = sold_count + 2 WHERE id = 1 AND quantity - sold_count >= 2`, потом проверить, что строка обновилась. Блокировка не держится, но для заказа из нескольких позиций откат сложнее.
3. **Уровень изоляции `SERIALIZABLE`** и повтор транзакции `DB::transaction($fn, 3)`. Так сделано у преподавателя в `WithdrawalService`. Конфликт находит сама база, но транзакции приходится повторять.

Для заказа из нескольких позиций первый вариант самый наглядный.

**Может ли случиться взаимная блокировка (deadlock)?**
Теоретически да: один заказ блокирует типы A и B, другой — B и A. Строки блокируются одним запросом `whereIn`, поэтому порядок обычно одинаковый. Для гарантии можно добавить `orderBy('id')`. Если дедлок всё же случится, PostgreSQL сам его обнаружит и откатит одну транзакцию, а `DB::transaction($fn, 3)` может её повторить.

**Что будет, если внутри транзакции выбросить исключение?**
`DB::transaction` откатит все изменения и пробросит исключение дальше. Например, на второй позиции не хватило билетов: `ValidationException` → откат (заказа нет, `sold_count` не изменился) → 422. Это проверяет `OrderTest::testCannotOrderMoreTicketsThanAvailable` (`assertDatabaseCount('orders', 0)`).

**Почему `increment` и `decrement`, а не `$type->sold_count += 2; $type->save()`?**
`increment('sold_count', 2)` превращается в один SQL-запрос `UPDATE ... SET sold_count = sold_count + 2`. Считает сама база, поэтому два одновременных запроса не затрут результат друг друга. Так вебхук безопасно возвращает резерв (`decrement`) даже без блокировки типа билета.

### Оплата

**Почему фронтенд не может сказать «оплата прошла»?**
Запрос фронта можно подделать: любой может отправить «я оплатил». Об оплате знает только платёжная система, и она сообщает нам напрямую, сервер к серверу, вебхуком с подписью. Это требование ТЗ §10.

**Как вы проверяете, что вебхук пришёл от платёжки, а не от злоумышленника?**
Подпись HMAC-SHA256. Платёжка сортирует поля, склеивает в строку `key|value|...` и считает HMAC с секретным ключом кассы. Ключ знаем только мы и платёжка. Мы пересчитываем подпись и сравниваем через `hash_equals`. Подделать подпись без ключа невозможно.

**Почему ваш `SignatureService` такой же, как у преподавателя?**
Подпись должна совпадать байт в байт: тот же порядок полей (`ksort`), тот же разделитель `|`, тот же алгоритм. Любая «улучшенная» версия просто не прошла бы проверку. Подписываются ровно те поля, что отправляются: 4 при создании платежа, 3 у вебхука.

**Почему `hash_equals`, а не `==`?**
`==` прекращает сравнение на первом несовпавшем символе, поэтому время ответа выдаёт, сколько символов угадано (timing-атака). `hash_equals` сравнивает за постоянное время.

**Что если вебхук придёт два раза?**
Платёжка повторяет отправку при ошибках, так что дубли возможны. Обработка идемпотентна: если заказ уже не `pending`, отвечаем 200 и ничего не меняем. Статус и остатки второй раз не изменятся, а когда появятся билеты, они не задвоятся.

**Что если вебхук вообще не придёт?**
Платёжка сама повторяет до 5 раз (1, 2, 4, 8 минут). Платёж висит 15 минут, потом она ставит `failed` и снова шлёт вебхук, и мы отменяем заказ и снимаем резерв. Страховка на случай, если вебхук потерялся совсем или `/pay` вообще не вызывали: команда `orders:expire` по расписанию (🛠 в планах).

**Почему ссылка на оплату — отдельный запрос `POST /orders/{order}/pay`?**
1. Создание заказа — короткая транзакция с блокировкой билетов. Запрос во внешнюю систему может идти секунды, его нельзя держать внутри транзакции.
2. Если платёжка недоступна, мы отвечаем 502, но заказ и резерв остаются. Фронт просто повторяет `/pay`, пользователю не нужно заново выбирать билеты.
3. Повторный `/pay` отдаёт ту же сохранённую ссылку, второй платёж не создаётся.

ТЗ §8 описывает шаги покупки, а §19 разрешает самим выбрать структуру API. Для фронта это два запроса подряд.

**Почему в платёжку уходит UUID, а не номер заказа?**
Платёжка требует, чтобы `order_id` был уникален в пределах кассы. После `migrate:fresh` или в тестах номера заказов снова начнутся с 1, и платёжка ответила бы «order_id уже занят». UUID уникален всегда. Он хранится в `orders.payment_reference`, по нему вебхук находит заказ. Заодно снаружи нельзя перебрать номера чужих заказов.

**Почему сумма умножается на 100 и зачем `round`?**
Платёжка принимает целое число в тийинах: 450 000 сум → `45000000`. `round` нужен, потому что `0.29 * 100` во float даёт `28.999…`, и простое `(int)` превратило бы это в 28.

**Почему 502, а не 500?**
500 — «сломались мы». 502 Bad Gateway — «мы работаем, но сервис за нами не ответил». Так фронт и логи сразу видят, где проблема.

**Почему неверная подпись — 403, а неизвестный заказ — 404, а не 500?**
Платёжка повторяет вебхук только на 5xx. Запрос с неверной подписью или по несуществующему заказу от повтора не исправится, поэтому отвечаем 4xx: «запрос плохой, не повторяй».

**Почему запрос в платёжку не внутри транзакции?**
Внутри транзакции держатся блокировки строк. Если платёжка отвечает 5 секунд, все остальные покупатели этих билетов 5 секунд ждут. Поэтому сначала короткая транзакция (резерв), потом HTTP-запрос.

**Что если платёжка недоступна?**
`Http::...->throw()` бросает исключение, `PaymentCreationService` превращает его в `PaymentSystemException`, контроллер отвечает 502 «Платёжная система недоступна, попробуйте позже». Заказ остаётся `pending` с резервом, `/pay` можно повторить.

**Откуда платёжка знает, куда слать вебхук?**
Из настроек кассы: `webhook_url` задаётся при создании кассы в интерфейсе платёжки. У нас это `http://host.docker.internal:<порт>/api/payments/webhook`: запрос идёт из контейнера платёжки, поэтому не `localhost`.

**Где хранится секрет и что будет, если он утечёт?**
В `.env` (`PAYMENT_SECRET`). В git он не попадает, в `.env.example` значение пустое. Если секрет утечёт, любой сможет подделать вебхук «оплачено». Тогда секрет нужно заменить и в платёжке, и в нашем `.env`.

### События, очереди, Scheduler

> Сейчас из этого работает только одно событие: `Registered` → listener `SendVerificationEmail` (письмо с кодом). События ТЗ §17, письма о покупке и напоминания — 🛠. Отвечай как о плане и понимании механизма.

**Зачем очереди?**
Отправка письма занимает секунды, к тому же SMTP может быть недоступен. Если делать её прямо в запросе, пользователь ждёт, а при ошибке запрос падает. В очереди задача выполняется отдельным процессом (`queue:work`) и повторяется при сбое. Драйвер очереди — `database` (`QUEUE_CONNECTION`), задачи лежат в таблице `jobs`.

**Зачем Events и Listeners?**
Это слабая связность. Код оплаты только сообщает «заказ оплачен» (`OrderPaid`), а кто на это реагирует (билеты, письмо, уведомление организатору), решают listeners. Новую реакцию можно добавить, не трогая логику оплаты. Так уже сделано с регистрацией: `AuthService` бросает `Registered`, а письмо отправляет `SendVerificationEmail`.

**Как будет работать напоминание за 24 часа?** 🛠
Scheduler раз в час запускает команду. Она находит мероприятия, которые начнутся через 24 часа, и ставит письма владельцам билетов в очередь. Чтобы письмо не ушло дважды, сохраняется отметка `reminder_sent_at`.

### Аутентификация и безопасность

**Почему не Breeze или Fortify?**
Их запрещает ТЗ: аутентификация сделана самостоятельно на Sanctum. Есть регистрация, подтверждение email кодом, логин (токен или cookie), logout с удалением токена. Основа написана в учебном репозитории курса, от которого сделан форк (подробно в §3).

**Чем отличаются режимы token и cookie?**
Для запросов со «своего» домена SPA (`SANCTUM_STATEFUL_DOMAINS`) используется сессия в cookie: токен не хранится в JS, XSS не сможет его украсть. Для остальных клиентов (Postman, мобильные) выдаётся Bearer-токен.

**Как защищён логин от перебора?**
Rate limiter: 3 неудачные попытки на email за 30 минут, регистрация не чаще 10 раз за 30 минут с одного IP. Заблокированный админом пользователь войти не может (но уже выданный токен продолжает работать, см. §3).

**Почему при неверном пароле, несуществующем email и блокировке ответ одинаковый?**
`AuthController::login` на любую ошибку отвечает 422 «invalid credentials». Так нельзя проверить, зарегистрирован ли email.

**Почему админ не может заблокировать или понизить сам себя?**
`UserPolicy::manage` проверяет `$user->id !== $model->id`. Иначе единственный админ мог бы случайно лишить себя доступа, и вернуть права было бы некому.

**Как защищены маршруты?**
Всё, кроме публичного чтения (мероприятия, категории, места, типы билетов) и вебхука, находится в группе `auth:sanctum`. Каждое действие дополнительно проверяется Policy. Вебхук без auth, но с проверкой подписи.

### Тесты

**Как тестировали?**
Feature-тесты на каждую фичу: успешный сценарий, права (401 гость, 403 чужая роль или чужая запись), валидация (422), бизнес-правила (например, нельзя купить больше остатка). База пересоздаётся на каждый тест (`RefreshDatabase`), данные берутся из фабрик. Внешнюю платёжку подменяем через `Http::fake()` и проверяем отправленный запрос через `Http::assertSent()`. Письма подменяем через `Mail::fake()`, события через `Event::fake()`. 🛠 Для очередей будет `Queue::fake()`.

**Сколько тестов и что покрыто?**
124 Feature-теста в 18 файлах. Из них 11 на оплату (`PaymentTest`): ссылка, повторный `/pay`, чужой заказ, гость, не `pending`, платёжка недоступна (502), успешный и неуспешный вебхук, неверная подпись, неизвестный заказ, повторный вебхук.

**Что такое TDD у вас?**
Для части фич сначала писали тест (что должно происходить), потом код, пока тест не станет зелёным. Это видно в истории коммитов («политика и TDD»).

## 3. Неудобные вопросы: слабые места и честные ответы

Здесь то, что можно «сломать» вживую или заметить в коде. Формула ответа: **признать → объяснить, почему так сейчас → сказать, как исправить**. Номера недочётов взяты из `05-PROGRESS.md`. Если вопрос про пункт из этого списка, покажи его: так видно, что проблема известна.

### Скорее всего спросят

**«Что из этого написано вами, а что взято?»**
Репозиторий — форк учебного репозитория курса (там платёжная система преподавателя). Из него остались: основа Docker-окружения, основа аутентификации (регистрация, вход по токену или cookie, подтверждение email кодом, rate limit, `AuthController`) и `SignatureService`, который обязан совпадать с платёжкой. Код самой платёжки удалён коммитом `63e298b`. Моё: роли, профиль, блокировка, категории, места, мероприятия с поиском, типы билетов, заказы с резервом, интеграция с оплатой и вебхук, все Policies и тесты к ним, рефакторинг на однометодные контроллеры.
*Совет:* не выдавай основу аутентификации за свою, но умей её объяснить: она в проекте.

**«По ТЗ админ управляет всеми сущностями. Почему он не может создать мероприятие или тип билета?»**
Решение такое: мероприятие всегда принадлежит организатору (`organizer_id` — тот, кто создал), а админ модерирует: редактирует, публикует, отменяет и удаляет любые мероприятия, меняет и удаляет любые типы билетов. Если админ должен создавать сам, это одна строка в `EventPolicy::create` и `TicketTypePolicy::create`, плюс решение, кто тогда будет организатором.

**«Можно купить билет на мероприятие, которое уже прошло?»** (№15)
Сейчас да, если его статус всё ещё `published`: автоматического перехода в `finished` пока нет, а `OrderCreationService` проверяет только статус (строка 19). *Исправление:* проверка `starts_at > now()` при покупке и команда в Scheduler, которая переводит прошедшие мероприятия в `finished`.

**«После продаж можно поменять дату или место?»** (недочёт №2)
Пока можно, это требование ТЗ §4 ещё не сделано. *Исправление:* в `EventService::update`, если у мероприятия есть проданные или зарезервированные билеты и меняются `starts_at`, `ends_at` или `venue_id`, отвечать 422. Рядом похожий недочёт №3: `quantity` типа билета можно поставить меньше `sold_count`.

**«Заблокированный пользователь со старым токеном продолжает работать?»** (№13, №18)
Да: блокировка проверяется только при входе (`AuthService::login`). *Исправление:* при блокировке удалять токены (`$user->tokens()->delete()`) или добавить middleware, как `BlockBannedUsersMiddleware` у преподавателя. Заодно: токены Sanctum сейчас бессрочные (`'expiration' => null` в `config/sanctum.php`), им можно задать срок жизни.

**«Деньги в `decimal`, а сумму заказа вы считаете во float?»** (№19)
Да: `$ticketType->price * $item->quantity` в PHP даёт float (`OrderCreationService.php:50`). Для сумм в сумах с двумя знаками точности float хватает, а при записи в `decimal(10,2)` значение округляется до тийинов. Строгое решение: считать через `bcmath` (`bcmul`, `bcadd`) или хранить суммы целым числом в тийинах.

**«Вебхук сверяет сумму?»** (№5)
Нет. Подпись уже гарантирует, что данные пришли от платёжки и не изменены, но сравнить `amount` с `total_amount × 100` — дешёвая дополнительная проверка. *Исправление:* одна проверка в `PaymentWebhookService`: при расхождении не ставить `paid` и записать в лог.

**«Что с заказом, по которому так и не нажали „Оплатить“?»** (№4)
Он остаётся `pending` и держит резерв бесконечно. Если `/pay` вызвали, платёжка сама через 15 минут пришлёт `status=2`, и резерв снимется. *Исправление:* поле `orders.expires_at` и команда `orders:expire` в Scheduler: переводит просроченные заказы в `expired` и возвращает `sold_count`.

**«Можно удалить мероприятие, на которое есть заказы?»** (№9)
Сейчас запрос падает с 500: внешний ключ `orders.event_id` не даёт удалить. Данные при этом не портятся, их защищает база. *Исправление:* перед удалением проверять заказы и отвечать 422 «есть заказы, отмените мероприятие вместо удаления». То же для категорий и мест, на которые ссылаются мероприятия.

### Если копнут глубже

**«Организатор может выпустить 1000 билетов в зал на 300 мест?»** (№16)
Сейчас да: сумма `quantity` типов билетов не сравнивается с `venues.capacity`. *Исправление:* в `TicketTypeService::create` и `update` считать сумму `quantity` всех типов мероприятия и при превышении вместимости отвечать 422.

**«Почему при регистрации проходит пароль из одного символа?»** (№17)
В `AuthRegistration` у пароля только `required` (основа из курса), а при смене пароля уже `min:8` (`ChangePasswordRequest`). *Исправление:* то же правило `min:8` при регистрации.

**«Зачем подтверждение email, если без него всё работает?»**
Код отправляется и проверяется, но доступ без подтверждения не ограничен. ТЗ подтверждение не требует, это функция из основы курса. *Если нужно:* закрыть покупку, проверяя `email_verified_at !== null` в `OrderPolicy::create`.

**«Если быстро два раза нажать „Оплатить“?»** (№7)
Проверка `payment_url !== null` идёт без блокировки, поэтому два одновременных запроса могут создать два платежа. На практике это редкость (двойной клик). *Исправление:* блокировка на уровне заказа (`Cache::lock("pay-{$order->id}")`) или middleware идемпотентности по заголовку `Idempotence-Key`, как у преподавателя.

**«А бесплатные билеты?»** (№6)
Цена 0 разрешена, но платёжка не принимает `amount = 0` (`min:1`), и `/pay` вернёт 502. *Исправление:* если `total_amount` равен 0, сразу переводить заказ в `paid`, без платёжки.

**«Типы билетов черновика видны всем?»** (№10)
Да: `GET /events/{event}/ticket-types` не проверяет видимость мероприятия, хотя карточка черновика уже отдаёт 404. *Исправление:* та же проверка `Gate::forUser(...)->denies('view', $event)`, что в `EventShowController`. Лучше сделать до защиты.

**«Мероприятие отменили. Участник с билетом открывает его страницу и видит 404?»** (№20)
Да: отменённое мероприятие видят только организатор и админ (`EventPolicy::view`). Свой заказ участник видит в `GET /orders/{id}`. Логичнее показывать отменённые мероприятия всем со статусом `cancelled` или хотя бы тем, у кого есть заказ. Решу вместе с уведомлениями об отмене (ТЗ §18).

**«Почему организатор не может купить билет?»**
По ТЗ покупка — действие участника, роли разделены (`OrderPolicy::create` пускает только `participant`). Организатор, который хочет пойти на чужое мероприятие, заводит отдельный аккаунт. Если нужно, правило меняется одной строкой в Policy.

**«Регистрация с полем `name` падает с 500?»** (№11)
Да: `toDTO()` в `AuthRegistration` и `LoginRequest` собирает DTO из `$this->all()`, а не из `validated()`, и лишнее поле ломает конструктор. В остальных Form Request уже `validated()`. Исправление — одно слово, лучше сделать до защиты.

**«Если открыть сайт в браузере?»** (№1)
Сейчас 500: `routes/web.php` ссылается на шаблон фронта платёжки, который удалён. Проект — только API, поэтому маршрут нужно удалить или отдавать простой ответ. Тоже до защиты.

**«Почему `AuthController` многометодный, если везде однометодные?»**
Он из основы курса и написан до рефакторинга. Остальные контроллеры переведены на `__invoke` в PR #11–#13, этот — в планах.

**«Почему Redis есть в Docker, но не используется?»**
Кэш и очереди сейчас на драйвере `database` (`CACHE_STORE`, `QUEUE_CONNECTION`). Redis заложен в окружение на будущее: чтобы перейти на него, достаточно поменять две переменные, код не меняется. Для учебной нагрузки `database` хватает, и задачи видны прямо в таблице `jobs`.

## 4. Базовые вопросы по Laravel

Короткие ответы, на 1–3 предложения. Подробности — по ссылкам в §5.

**Как проходит запрос в Laravel?**
`public/index.php` → приложение из `bootstrap/app.php` → глобальные middleware → роутер находит маршрут → middleware маршрута (`auth:sanctum`, `can:`) → Laravel создаёт Form Request и проверяет его → контроллер → ответ. Ошибки для `api/*` превращаются в JSON (`shouldRenderJsonWhen` в `bootstrap/app.php`).

**Что такое Service Container и как сервис попадает в контроллер?**
Контейнер создаёт объекты и подставляет зависимости по типу. В `__invoke(..., OrderCreationService $service)` Laravel создаёт сервис сам. Для интерфейса нужна привязка: `SignatureContract` → `SignatureService` в `AppServiceProvider::register()` (`singleton`, один экземпляр на приложение).

**Зачем интерфейс `SignatureContract`?**
Код зависит от интерфейса, а не от класса, поэтому реализацию можно подменить, например в тесте через `$this->mock(SignatureContract::class)`.

**Что такое middleware?**
Фильтр вокруг запроса. У нас: `auth:sanctum` (кто ты), `can:` (можно ли), `throttle:login` (не слишком ли часто).

**Как устроены связи в Eloquent?**
Связь — метод модели: `Event::ticketTypes()` — `hasMany`, `TicketType::event()` — `belongsTo`, `Order::items()` — `hasMany`. Laravel строит по ним SQL-запросы.

**Что такое проблема N+1?**
Список из 15 заказов, и для каждого отдельный запрос за строками заказа: 16 запросов. `Order::with('items')` в `OrderListService` загружает все строки одним запросом, итого 2.

**Что такое mass assignment и `#[Fillable]`?**
`Model::create($array)` и `fill()` записывают только поля из `#[Fillable]`. `status`, `organizer_id`, `sold_count` туда не входят и задаются в сервисе явно. Защита у нас двойная: лишние поля отсекает уже `validated()` при сборке DTO, а `#[Fillable]` не даст записать служебное поле, даже если оно туда попадёт. Это проверяет `EventTest::testClientCannotSetStatusOrOrganizerOnCreate`.

**Что делают касты?**
`casts()` в модели: строку из базы превращает в enum (`EventStatus`), `datetime` — в объект даты (Carbon), `decimal:2` — в строку с двумя знаками, `hashed` у пароля автоматически хэширует его при сохранении.

**Что такое миграции?**
Описание схемы БД в коде, с версиями: `migrate` применяет, `migrate:rollback` откатывает. Внешние ключи — `foreignId()->constrained()`, `cascadeOnDelete()` удаляет зависимые записи (типы билетов вместе с мероприятием).

**Где Sanctum хранит токен?**
В таблице `personal_access_tokens` лежит только SHA-256 хэш. Открытый токен (`plainTextToken`) клиент получает один раз при входе и шлёт в заголовке `Authorization: Bearer <token>`. Logout удаляет запись. Для SPA со «своего» домена — cookie-сессия с CSRF (`statefulApi()` в `bootstrap/app.php`).

**Как работает валидация?**
Laravel создаёт Form Request до вызова контроллера и проверяет `rules()`. Ошибка → 422 с ошибками по полям, контроллер не вызывается. Правила в проекте: `after:now`, `after:starts_at`, `exists:categories,id`, `distinct`, `in:date,-date,price,-price`.

**Что дают фабрики и `RefreshDatabase`?**
Фабрика генерирует тестовые записи: `User::factory()->create(['role' => UserRole::Organiser])`. `RefreshDatabase` один раз прогоняет миграции и оборачивает каждый тест в транзакцию, которая потом откатывается, поэтому тесты не влияют друг на друга. Тесты идут в отдельной схеме `test_schema` (`phpunit.xml`).

**Какие HTTP-коды и когда?**
200 — успех, 201 — создано, 401 — не вошёл, 403 — нельзя, 404 — нет записи или она скрыта, 422 — ошибка данных или бизнес-правила, 429 — слишком часто, 502 — внешний сервис не ответил.

**Что такое REST в вашем API?**
Ресурсы — существительные в URL (`/events/5/ticket-types`), действие — HTTP-метод. Действия, которые не укладываются в CRUD, оформлены отдельными `POST`: `/events/{event}/publish`, `/cancel`, `/orders/{order}/pay`.

## 6. Глоссарий

| Термин | Простыми словами |
|---|---|
| REST API | адреса-«ресурсы» (`/events/5`) и HTTP-методы (GET читать, POST создать, PUT заменить целиком, PATCH изменить часть, DELETE удалить) |
| Middleware | фильтр перед контроллером (например, «пользователь авторизован?») |
| Policy | класс с правилами «кто что может делать с моделью» |
| Form Request | класс с правилами валидации входных данных |
| Транзакция | группа операций с БД: либо все применяются, либо ни одна |
| `lockForUpdate` | блокировка строки до конца транзакции, другие ждут |
| Race condition | два процесса одновременно читают и пишут одни данные, и результат ломается |
| Deadlock | две транзакции ждут друг друга бесконечно; PostgreSQL обнаруживает это и откатывает одну |
| Webhook | запрос, который внешний сервис сам отправляет нам при событии |
| HMAC | подпись сообщения секретным ключом, подтверждает автора и целостность |
| Timing-атака | подбор секрета по тому, сколько времени сервер тратит на сравнение |
| Идемпотентность | повтор одного и того же запроса не меняет результат |
| Queue / Job | фоновая задача, выполняется отдельным процессом |
| Scheduler | планировщик, запускает команды по расписанию (как cron) |
| DTO | простой объект только для переноса данных |
| Однометодный контроллер | контроллер с единственным методом `__invoke`, одно действие на класс |
| `scopeBindings` | поиск вложенной модели из URL только внутри родительской |
| Mass assignment | массовое заполнение модели из массива; защищается списком `#[Fillable]` |
| N+1 | лишний запрос в БД на каждый элемент списка; лечится `with()` |
| Factory | генератор тестовых записей для моделей |
